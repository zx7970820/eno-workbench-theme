迁移的第一天很容易只记住启动速度：原来开发服务要等 38 秒，换成 Vite 后几秒就能看到页面，HMR 也快了很多。真正暴露问题的往往是第二天的测试：别名没有在 runner 里生效，某个只提供 CommonJS 入口的依赖在浏览器里能跑，Node runner 却报错。

迁移并不是把速度问题换成另一个速度问题，而是把原来藏在 webpack loader 和插件里的约定摊到了桌面上。每一条约定都要重新确认。

先列出旧配置真正做了什么

不要从 webpack.config.js 逐行翻译。那样很容易把插件名字搬过去，却忘记它们原本在解决什么问题。先把旧配置分成几类：模块路径、环境变量、资源处理、代码分割、开发服务器代理和测试入口，然后为每一类写一个最小验证。

例如 alias 不只是“路径更短”，它决定了应用代码和测试代码是否会加载同一份模块：

// vite.config.ts
resolve: {
  alias: {
    '@': fileURLToPath(new URL('./src', import.meta.url)),
  },
},

给 @/shared/version 加一条导入冒烟测试，同时从浏览器入口和测试入口各运行一次。这样问题一出现，就能知道是 alias 没生效，还是 runner 的 ESM 配置不同，而不是在 CI 里盲目地删 node_modules。

环境变量也有类似陷阱。Vite 默认只把 VITE_ 前缀暴露给客户端，旧项目里叫 PUBLIC_API 的变量迁移后会变成 undefined。把变量分成客户端可见和服务端专用两张表，启动时只打印变量名，不打印值，并让构建在缺少必需变量时尽早失败。

依赖预构建不是缓存魔法

Vite 会把很多依赖预构建成浏览器更容易加载的形式，结果放在 .vite 目录。大多数时候它很安静，出问题时却会表现得很像“代码没更新”：升级一个包后，旧的导出仍然在页面里，重启开发服务还不一定消失。

遇到“代码没更新”时，直接删缓存可能只会让页面暂时恢复。先看 optimizeDeps 的实际结果：锁文件、Node 版本或依赖的 package exports 发生变化时，预构建入口可能已经不同。清理缓存应该有明确条件，普通的组件改动不需要清缓存。

pnpm vite --host 0.0.0.0
pnpm vite --debug

--debug 的输出比“试着再跑一次”有用得多，它能看到哪些依赖被扫描、哪些包被排除。对于一个只在生产构建中出现的 CommonJS 包，我宁愿先加一条很小的兼容配置，也不把所有依赖都塞进 optimizeDeps.include。

测试环境必须单独验收

浏览器里的 Vite 运行时和测试 runner 不是同一个环境。前者会处理 ESM、资源 URL 和浏览器全局对象，后者可能在 Node 中直接执行模块。迁移后最先失败的测试通常不是业务逻辑，而是 window、路径别名、CSS 导入或动态 import 的假设。

可以把 alias 定义抽成一份小模块，在 Vite 和测试配置中共同使用；对必须依赖浏览器的测试，明确使用 jsdom；对纯函数测试，保持 Node 环境。这样配置差异是有意的，而不是由两个文件慢慢漂移出来的。

速度要换算成团队时间

只看开发服务启动时间会高估迁移收益。还要记录冷缓存和热缓存的构建时间、HMR 后页面恢复时间、CI 总时长、产物大小以及类型检查时间。迁移后本地启动可能快了，但类型检查变成并行任务，CI 反而需要重新安排顺序；如果不把这些时间放在一起，结论会很片面。

迁移期间保留旧构建命令，直到主要页面、测试和发布产物都跑过。遇到问题时按症状分流：浏览器错误看转换后的模块，测试错误看 runner，构建错误看插件钩子和最终产物。工具换掉了，排查方法不能也一起丢掉。
