迁移后启动从 38 秒降到 1.4 秒，第二天 CI 却因 alias、环境变量和测试 runner 差异失败。我把旧配置里的 alias、define、静态资源、动态 import 和变量前缀列成契约逐条确认。遇到 HMR 失效先确认模块是否被 server 转换，再清 .vite 缓存，而不是立刻禁用 HMR。速度提升是真的，配置债务只是换了位置。

迁移里最容易漏的是测试

应用在浏览器里能跑，不代表 Node 测试环境能跑。Vite 的 ESM、测试 runner 的 transform、服务端别名解析是三套配置。我们把同一份 alias 定义抽出来，并写一个导入路径冒烟测试，避免 CI 到最后才发现某个包只在 webpack loader 下成立。

依赖预构建缓存写进本地后，升级依赖时偶发旧结果。我把锁文件变化作为清缓存条件，并在问题报告里记录 optimizeDeps 的实际结果。动态 import 还需要确认产物是否真的拆分，不能只看文件数量。

迁移检查清单：开发和 CI 分别跑一次；确认环境变量前缀；检查 CommonJS 包；验证 alias、静态资源和动态 import；记录冷启动与热更新；保留回滚分支。

速度要用团队时间衡量

启动快只是一个指标。我还记录首次测试反馈、HMR 后页面恢复时间、CI 构建和产物体积。某个插件迁移后构建快了，但类型检查变慢，综合收益没有想象中大。

pnpm vite --host 0.0.0.0
pnpm build -- --debug

迁移完成后保留旧构建一段时间，遇到依赖不兼容可以快速对照。工程工具更换的风险不在命令，而在隐含契约。

迁移后的配置需要有人负责，不然半年后又会出现两套 alias 和两套环境变量规则。我们把关键决定写进 README，并给新包接入准备最小模板。工具升级的收益只有被团队吸收，才不是一次性的个人技巧。

还有一个现实问题：团队成员本地缓存和 Node 版本不同，会把迁移问题伪装成偶发故障。我们固定 Node 版本，CI 先执行冷缓存构建，再执行热缓存构建。错误报告中附带依赖预构建列表和完整版本号，排查速度比“删 node_modules 再试”稳定得多。

最终迁移文档没有写成插件清单，而是写成遇到问题怎么判断：浏览器错误看转换结果，测试错误看 runner 环境，构建错误看产物和插件钩子。按症状分流比记住几十个开关更有用。

在实际维护中，我会把这类问题保留一份最小复现和一份线上证据。最小复现用来验证修复，线上证据用来确认修复没有改变其他路径。发布前再检查日志、指标、回滚和权限四件事，很多看似完成的改动，最后都卡在其中一件。

这份记录也提醒我，不要把解决方案写成只适用于当前机器的命令。配置、数据规模和失败路径都要写出来，下一次遇到相似症状才能快速判断哪些条件仍然成立。

在代码审查时，我会要求作者把这条经验落成一个可观察的检查点：一个测试、一个指标或一条部署校验都可以。只有能被下一次运行验证，经验才不会停留在事故后的口头总结。

如果这条检查没有自动化入口，就先补一个最小脚本或测试。它不需要覆盖所有情况，但必须能在改动后重复运行，并把失败原因留在构建日志里。
