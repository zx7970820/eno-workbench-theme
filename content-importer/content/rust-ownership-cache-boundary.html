配置缓存原本设计成 Arc<Mutex<HashMap>>，读路径也要拿锁。后来更新时构造新快照，读者只拿 Arc<Config> 的不可变引用，锁只保留在真正修改共享状态的边界。所有权迫使我说清谁能改、什么时候改，调用方不再暴露 guard，也不在持锁期间做 IO。Rust 不是没有锁，而是让锁的必要性变得可见。代码：

struct Store { current: Arc<Config> }
fn read(&self) -> Arc<Config> { Arc::clone(&self.current) }

第一版为什么还是用了锁

配置更新最初来自多个线程，我担心读写竞争，所以先用 Mutex 包住全部 Map。编译器没有阻止这个设计，它只保证这个设计不会产生未定义行为。真正的问题是锁的生命周期太长，读者拿着 guard 进行格式化和日志写入，尾延迟跟着上升。

改成快照后，更新线程构造新 Config，完成校验后一次性替换 Arc。失败的配置不会污染当前版本，读者永远看到完整快照。代价是更新时会短暂分配更多内存，所以大对象场景要测复制成本，不能把“无锁”当成免费。

检查清单：读路径是否只需不可变引用；更新是否可以构造新快照；校验失败是否保留旧版本；guard 是否跨越 IO；基准是否同时测读延迟和更新内存峰值。

什么时候快照反而不划算

配置很小的时候快照几乎没有成本，大文档或大字典则可能在更新高峰制造分配尖峰。我用 criterion 比较读取延迟和更新峰值，必要时把大字段拆成不可变分片，而不是回到全局 Mutex。

let next = Config::parse(raw)?;
validate(&next)?;
store.swap(Arc::new(next));

这段顺序很重要：先解析、再校验、最后替换。任何失败都保留旧配置，读者不需要处理半成品状态。

如果未来需要热更新配置，我会先保留旧 Arc 一段时间，让正在执行的请求自然完成，而不是强行让它们看到新值。这个取舍要结合请求时长评估。类型系统保证安全，具体的版本语义仍然需要业务自己定义。

调试时我还给 Config 增加版本号和来源字段，日志能回答当前请求读到哪一版配置。更新失败只记录错误，不替换旧快照。这个小字段非常有用：没有它，线上看到错误结果时很难判断是旧配置、半更新还是读取线程的问题。

这套设计也让审计更容易：日志中的版本和配置 hash 可以对应发布记录，但不直接记录敏感配置。读取 API 只返回需要的字段，所有权边界和安全边界一起收紧，比事后加脱敏更可靠。

在实际维护中，我会把这类问题保留一份最小复现和一份线上证据。最小复现用来验证修复，线上证据用来确认修复没有改变其他路径。发布前再检查日志、指标、回滚和权限四件事，很多看似完成的改动，最后都卡在其中一件。

这份记录也提醒我，不要把解决方案写成只适用于当前机器的命令。配置、数据规模和失败路径都要写出来，下一次遇到相似症状才能快速判断哪些条件仍然成立。

在代码审查时，我会要求作者把这条经验落成一个可观察的检查点：一个测试、一个指标或一条部署校验都可以。只有能被下一次运行验证，经验才不会停留在事故后的口头总结。
