Vite 的启动速度很容易让人先记住一个数字：从几十秒变成几秒。但真正排查问题时，数字没有那么有用。要看的是浏览器请求了什么、依赖有没有被预构建、HMR 找到了哪一条边界，以及生产构建是否走了另一套流程。

Vite 的速度来自浏览器原生 ESM 驱动的按需转换，依赖预构建和底层转换器只是其中一部分。把这几条路径分开，很多“开发环境没问题、测试或生产出错”的现象就不再神秘。

先回看旧开发服务器为什么慢

传统开发服务器通常先遍历入口、构建完整模块图并生成开发 bundle，服务器准备好后浏览器才能加载。项目变大时，即使只修改一个叶子模块，启动阶段仍可能付出全图处理成本。

Vite 把模块分成两类：

  • 依赖：通常来自 node_modules，变化少，体积大，模块格式可能混杂。
  • 源码：频繁修改，通常是现代 ESM，需要按请求转换。

开发服务器先处理稳定依赖；业务源码则在浏览器请求到对应 URL 时才转换。首页未触达的路由，不必阻塞首次启动。

依赖预构建有两个目的

第一，兼容 CommonJS/UMD。浏览器不能直接执行 Node 风格模块，预构建会把它们转换为 ESM。

第二，减少请求数量。有些 ESM 依赖内部包含数百个小模块；如果原样交给浏览器，会产生大量请求。Vite 把这类依赖合并成更少的模块，以换取稳定、可缓存的加载。

预构建结果基于 lockfile、补丁目录、配置和环境等信息缓存。依赖没有变化时，重启不应重新做同样的工作。遇到依赖被错误缓存，可以显式强制优化，但不应把“每次启动都清缓存”当成常规脚本。

源码转换由 HTTP 请求驱动

浏览器请求 /src/main.ts，Vite 转换 TypeScript、重写裸模块导入，再返回可执行 ESM。随后浏览器解析其中的 import 并继续发出请求，模块图逐步展开。

这带来一个重要结论：开发阶段的“模块”天然对应 URL。插件的 resolveId、load、transform 仍然构成转换管道，但它们工作在按需请求上，而不是必须先输出完整 bundle。

如果一个插件在每次 transform 中做全项目扫描，Vite 的架构优势仍会被抵消。插件性能应关注单请求开销、缓存键和是否不必要地使大量模块失效。

HMR 是沿模块图寻找接受边界

文件变化后，Vite 并不是简单地重新加载这个文件。它要沿导入关系向上查找 HMR boundary：某个模块显式接受自身或依赖更新，并知道如何把新实现接入当前状态。

if (import.meta.hot) {
  import.meta.hot.accept('./state.js', (newModule) => {
    store.replace(newModule.createState())
  })
}

框架插件会为组件生成更细粒度的接受逻辑。如果更新一路传播到入口仍没有模块接受，就必须整页刷新，因为运行时无法安全地保留旧状态。

因此 HMR 慢或频繁全刷新的排查重点是：

  • 哪个模块成为过宽的共享依赖？
  • 是否把副作用和纯导出放在同一个模块？
  • 插件是否返回了稳定的模块边界？
  • CSS、组件和状态是否能独立接受更新？

为什么开发快不代表生产不打包

原生 ESM 的大量请求适合本地低延迟环境，却不一定适合公网。生产构建仍需要 Tree Shaking、代码分割、资源哈希、CSS 提取、压缩和兼容性处理。

这意味着开发与生产并非完全相同的执行路径。某些仅在构建期出现的问题——动态导入分析、公共基础路径、Chunk 循环依赖、旧浏览器目标——必须通过 vite build 和真实部署预览验证，不能只依赖 dev server。

大型项目里 Vite 也会慢在哪里

  1. 浏览器要请求和解析的模块过多，首屏瀑布变长。
  2. TypeScript 类型检查、ESLint、代码生成与测试被同步塞进启动路径。
  3. 插件在 transform 中做昂贵 I/O，或没有缓存。
  4. 一个基础模块被大量页面依赖，修改后失效范围巨大。
  5. monorepo 中的链接包未被正确预构建，模块格式反复转换。

优化时应分别量化服务器启动、依赖预构建、单模块转换、浏览器请求瀑布和 HMR 更新时间。只看“ready in 300ms”不能代表页面已经可交互。

从 Webpack 迁移时要重新检查什么

  • process.env、require.context 和 Node 内置模块不能原样搬到浏览器。
  • 公共路径改由 base 和 URL 语义管理。
  • 插件钩子虽然接近 Rollup，但并非 Webpack Plugin 的一一对应。
  • 动态导入必须让构建器可分析，过度动态的字符串会破坏预加载和分块。
  • 开发服务器代理只解决本地跨域，不是生产网关配置。

迁移成功的标准不是“开发服务器启动了”，而是开发、构建、预览、资源路径、懒加载和错误监控都在目标部署环境下成立。
