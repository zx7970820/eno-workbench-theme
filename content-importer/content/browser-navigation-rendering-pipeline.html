打开 Performance 面板，经常会看到几个容易被混成一句话的时间点：Network 已经没有请求了，主线程还在跑长任务；DOMContentLoaded 已经触发了，最大那块内容还没出现；滚动时主线程没什么事，合成线程却在忙。它们都被叫作“页面加载”，其实对应的是不同阶段。

下面不从“浏览器收到 HTML 后开始渲染”这句大话讲起，而是沿着一次导航，把能观察到的产物挨个对上：从 URL 和缓存，到首字节、DOM/CSSOM、布局、绘制、分层、光栅化与合成。八段是排查时的一条观察顺序，不是浏览器源码里从头走到尾的同步流水线。

1. 地址栏回车后，第一件事不是 DNS

浏览器先解析 URL：协议、主机、端口、路径、查询参数和片段分别是什么。片段只影响当前文档里的定位，不会被发送给服务器；真正决定请求目标的是前面的部分。

接下来浏览器会检查几层可能的已有结果：

  • 直接命中的内存缓存或磁盘缓存。
  • Service Worker 是否接管了这个 origin 的请求。
  • 当前连接是否还能复用，而不是每次都重新建连接。

如果没有可直接使用的响应，才会进入网络阶段。这里已经有一个常见误区：地址栏按下回车，不一定意味着每次都从 DNS 开始，也不一定每次都重新做 TCP 和 TLS。

2. 什么时候才算拿到第一个字节

没有缓存时，主机名要先解析成 IP。之后浏览器可能建立 TCP 连接，再完成 TLS 握手；使用 HTTP/3 时，底层则是基于 QUIC 的连接。握手完成后才会发出 HTTP 请求。

服务器响应到达的时间，通常先看 TTFB（Time to First Byte）：它包含了连接、握手、服务器处理和响应开始传输前的等待。TTFB 很长时，继续调 CSS 和 JavaScript 没有意义，页面还没拿到可以解析的字节。

响应也不是一定要等完整文件下载完才开始处理。HTML 是流式到达的，浏览器拿到一部分字节后就可以继续往下解析。HTTP/2 或 HTTP/3 的多路复用能减少连接层面的等待，但不能消除服务端慢、资源太多或主线程被脚本占满的问题。

3. 解析器为什么会被一个 script 拦住

主线程拿到 HTML 字节后，会解码、分词、构建 DOM。解析器读到普通文本就继续前进，遇到元素开始标签就创建节点，遇到结束标签就回到父节点。

浏览器还有一个并行的预加载扫描器。它不负责构建最终 DOM，而是快速扫 HTML 里已经出现的 link、script、img 等资源，尽早发起请求。它能把网络等待和 HTML 解析重叠起来，但看不到 JavaScript 运行后才拼出来的 URL。

经典的外链脚本会改变解析节奏：

<script src="app.js"></script>

没有 async、defer 或 type="module" 时，解析器遇到它通常要先等脚本下载并执行，再继续解析后面的 HTML。脚本可以读取前面已经创建的 DOM，也可以直接修改文档，所以浏览器不能假设它没有副作用。

这就是为什么把一个普通脚本放在 head 里，可能让页面看起来很久没有内容；脚本不是“在后台下载”，而是把解析器挡在了当前位置。

4. DOM 有了，为什么还不能画

HTML 解析得到 DOM，CSS 解析得到 CSSOM。DOM 表达“有哪些节点以及它们怎样嵌套”，CSSOM 表达“每条 CSS 规则如何匹配、继承和计算”。

document.documentElement
// DOM 的根节点

样式表不只是下载文件。浏览器还要解析选择器、处理层叠和继承。遇到外链样式表时，浏览器通常会把它视为渲染前必须准备好的资源；否则先画一版默认样式，再突然换成正式样式，页面会出现明显的无样式闪烁。

JavaScript 又会把这两棵树交叉起来：脚本可以读取 DOM，也可以读取样式相关属性并修改节点。解析、脚本和样式之间的依赖关系，决定了“拿到 HTML”离“能画出来”还有多远。

5. render tree 不是 DOM 的复制品

浏览器会遍历 DOM，把匹配到的 CSS 规则合并成每个节点的计算样式。这个结果常被叫作 render tree，但它不是把 DOM 原样复制一份：

  • display: none 的节点不会进入渲染树，因为它不占布局空间。
  • visibility: hidden 的节点仍会占空间，只是不绘制内容。
  • 伪元素、匿名盒和替换元素可能在渲染阶段出现额外的盒子。

这一阶段会产生 style recalculation。修改 class、父节点的继承属性或大量选择器，都可能让浏览器重新匹配一批节点。样式计算完成后，浏览器才有足够信息进入几何计算。

6. Layout 到底在算什么

Layout（也叫 reflow）要回答的是几何问题：每个盒子多宽、多高，放在什么坐标，子节点如何影响父节点，文字换行后父节点是否需要变高。

块布局、行内布局、Flex、Grid、绝对定位和滚动容器都有自己的约束。一个元素尺寸变化，可能沿着父子关系影响很多节点；窗口旋转、字体加载完成和图片拿到固有尺寸，也都可能触发新的 layout。

const width = element.offsetWidth
element.classList.add('expanded')
const nextWidth = element.offsetWidth

这类代码可能把读写交错成强制同步 layout：第二次读取需要先把刚才的样式修改算完。批量写入后再批量读取，通常比读写交替更容易让浏览器安排工作。

transform 和 opacity 经常可以绕开几何计算，但不是所有动画都自动变快。元素最终还要经过绘制、分层和合成，是否更快需要用 Performance 面板验证。

7. Paint 之后，浏览器才决定哪些内容单独合成

Layout 只知道盒子在哪里，还没有把文字、背景、边框和阴影画成像素。Paint 会根据这些几何和计算样式，生成一组绘制指令：填充背景、画边框、绘制文字、贴图像、应用阴影和裁剪。

现代浏览器通常先生成 paint chunks 或 display items，再进行 layerization。分层不是“每个元素一个图层”，而是浏览器根据滚动、动画、裁剪、视频、position: fixed、transform 或 will-change 等因素，决定哪些绘制内容值得放进独立的 composited layer。

独立图层有一个直接好处：只移动或改变这个图层时，不必重新绘制页面中所有兄弟节点。但图层也占内存，过度使用 will-change: transform 会让纹理数量暴涨，反而增加上传和合成成本。分层是实现手段，不是性能奖章。

8. 光栅化完成，合成线程把画面交给屏幕

Paint 的绘制指令还不是 GPU 可以直接显示的位图。较大的图层会被切成 tiles，光栅线程把每个 tile 里的文字、颜色、图片和阴影栅格化成像素数据，通常再上传或保存在 GPU 纹理中。

合成线程负责把各个图层当成一组 quads，按照位置、裁剪、透明度和变换组合起来，提交给 GPU。滚动一个已经栅格化的图层时，合成线程可能只需要移动纹理，不必让主线程重新执行 JavaScript、样式计算、layout 和 paint。

可以把最后一段想成这样：

paint chunks
  -> layer tree
  -> tiles
  -> raster threads / GPU textures
  -> compositor quads
  -> vsync
  -> screen

如果某个 tile 失效，浏览器只重栅格化受影响的区域；如果布局变化，前面的阶段也可能全部重新走一遍。60Hz 屏幕一帧大约只有 16.67ms，但这个数字不是“每个阶段各有 16.67ms”，而是这一帧所有主线程、合成和 GPU 工作的总预算。

这八步不是一条严格的流水线

真实浏览器会并行和交错执行：网络线程继续收资源，HTML 解析器继续推进，图片解码可能在别的线程，主线程处理脚本和样式，合成线程又在准备下一帧。页面也可以渐进式显示，不必等完整 DOM 和所有图片都结束才第一次绘制。

所以遇到“页面慢”，我会先把现象对应到阶段：

  • 首字节晚：看 DNS、连接、服务器处理和缓存。
  • HTML 有了但页面空白：看解析器阻塞脚本、CSS 和长任务。
  • LCP 晚：看关键资源、样式计算、layout 和最大内容元素的 paint。
  • 滚动掉帧：看主线程长任务、强制 layout、paint 面积和图层合成。
  • 动画卡顿：看是否每帧都触发 layout/paint，还是可以交给合成线程。

知道每一步在产出什么，DevTools 的 Network、Performance、Layers 和 Rendering 面板才会连成一条线。否则看到“浏览器渲染很复杂”，仍然不知道应该先查哪一层。
