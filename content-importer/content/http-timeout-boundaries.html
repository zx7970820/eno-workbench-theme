我第一次只写 request.setTimeout(5000)，连接池仍然被拖满。一个请求有 DNS、连接、读取、数据库和业务阶段，时间预算应该从入口往下游传。入口生成 deadline，下游只使用剩余时间，日志区分 connect_timeout、read_timeout 与 deadline_exceeded。AbortController 还要和响应体消费、连接复用一起考虑。超时不是越短越好，它来自用户能接受的延迟、下游 p99 和重试次数。代码：

const deadline = Date.now() + 1800
const remaining = () => Math.max(0, deadline - Date.now())

重试把问题放大过

旧代码在下游超时后自动重试两次，入口又有一次重试。一次慢查询就可能变成九个数据库请求。我的第一个修复是把所有重试删掉，结果网络偶发抖动时错误率明显变高。后来改成只对连接建立失败重试一次，并把每次重试消耗的剩余预算写进日志。

代码里还要区分客户端断开和服务端超时。客户端已经断开时继续做昂贵的序列化没有意义，AbortSignal 要传到数据库和下游 HTTP。测试不能只测成功路径，要模拟 DNS 慢、连接成功但响应体慢、数据库锁等待和客户端提前断开。

交付前我会检查：入口 deadline 是否唯一；每个下游是否使用剩余时间；重试是否受预算约束；响应体是否释放；日志是否区分阶段；指标是否包含 timeout 类型。

测试场景要故意不舒服

我写了一个假的下游服务，分别模拟连接建立慢、返回头慢、返回体只发一半、响应后继续占用连接。每一种情况都验证入口是否在 deadline 前结束，并检查连接池数量是否回落。

curl --max-time 2 http://127.0.0.1:8080/proxy

另外，超时错误不能原样返回给用户。内部日志需要保留阶段和剩余预算，外部只返回稳定的错误码。这样既方便排查，也不会把下游地址和重试细节暴露出去。

这次之后，接口契约里也写了超时语义：客户端最多等待多久、服务端愿意保留请求多久、下游失败返回什么。文档和实现一起改，避免调用方根据一个模糊的“超时 5 秒”继续叠加重试。测试数据则固定保存，方便版本升级后复跑。

最后我把超时预算加入接口测试的断言，避免未来有人加一个下游调用却没有减少自己的预算。压测报告同时列出成功请求、超时请求和取消请求，三者混在一起会掩盖真实体验。代码评审里凡是新增网络调用，都必须回答它使用谁的 deadline。

超时配置还要避免通过环境变量随意放大。线上允许调整的范围应有上下限，并在启动日志中输出最终值。否则某次临时排障把超时调到很大，可能一直留在生产而没人察觉。

在实际维护中，我会把这类问题保留一份最小复现和一份线上证据。最小复现用来验证修复，线上证据用来确认修复没有改变其他路径。发布前再检查日志、指标、回滚和权限四件事，很多看似完成的改动，最后都卡在其中一件。

这份记录也提醒我，不要把解决方案写成只适用于当前机器的命令。配置、数据规模和失败路径都要写出来，下一次遇到相似症状才能快速判断哪些条件仍然成立。
