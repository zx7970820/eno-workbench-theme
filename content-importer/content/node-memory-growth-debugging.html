线上报警是在午饭后来的一次。RSS 每十分钟涨一点，但 heapUsed 很稳定。我先记录 process.memoryUsage()，把 heap、rss、external 分开看，再比较两次 heap snapshot 的 Retainers。最后找到一个按租户缓存配置的 Map 没有 TTL，键还是完整 URL。修复不是简单 clear，而是限制条目数、加过期策略，并给命中率和淘汰次数打点。经验是先区分 heap 与 rss，再用快照解释引用链，最后给缓存加生命周期。代码：

setInterval(() => console.log(process.memoryUsage()), 60000)

当时误判了什么

我一开始把 RSS 增长归到 V8 碎片化，因为 heapUsed 看起来很平。这个判断并非完全错误，但它让我浪费了半小时去调 max-old-space-size。真正有用的是比较快照里的对象数量和 retained size，并把请求完成后的缓存引用画成一张图。缓存 key 来自 URL，query 参数顺序不同还会产生重复条目，这是第二个隐蔽问题。

上线前的检查

我在压测里加入长时间运行而不是只跑吞吐：观察十分钟、三十分钟和两个小时三个窗口；同时记录 heapUsed/rss、缓存条数、命中率、GC pause。限制条目数解决不了错误的 key 归一化，所以先统一 URL，再做 TTL 和上限。最后保留一个低频 heap snapshot 入口，只允许内网和短时启用。

可复用清单：先分 heap 与 rss；再比较两次快照；顺着 Retainers 找持有者；给缓存设置 TTL、容量和指标；不要用重启证明修复有效。

另一条验证路径

为了确认不是流量变化，我把同一批请求回放到两份容器：一份启用缓存，一份禁用缓存。禁用缓存的 RSS 平稳但数据库变慢，启用缓存的 RSS 继续上升，这才把范围缩到缓存生命周期。还要注意快照会让进程短时变慢，我只在低峰期抓取，并给诊断开关设置自动关闭时间。

修复后我没有立刻删除缓存，而是先把 TTL 调到很短，确认曲线停止上涨，再逐步恢复容量。这个过程能区分“修复生效”和“业务只是少了流量”。

最后我把这次排障写进运行手册：报警先看哪三个图、什么情况下抓快照、谁有权限打开诊断开关。新人不必复述我的猜测，只要按顺序收集证据。线上问题的价值不只在修好当前进程，也在于下一次能更早分辨同一种故障。

为了防止回归，我给缓存增加了最大 key 长度和规范化函数，并把缓存条数暴露到健康诊断接口。诊断接口只返回聚合信息，不返回租户配置内容。每次升级依赖后跑一次长稳测试，内存问题通常不会在五分钟单测里出现。

内存指标要按版本和实例分组，不能只看一条集群平均线。平均值会掩盖某个实例持续泄漏。滚动发布时比较旧实例和新实例的斜率，往往比等到总量报警更早发现回归。

在实际维护中，我会把这类问题保留一份最小复现和一份线上证据。最小复现用来验证修复，线上证据用来确认修复没有改变其他路径。发布前再检查日志、指标、回滚和权限四件事，很多看似完成的改动，最后都卡在其中一件。

这份记录也提醒我，不要把解决方案写成只适用于当前机器的命令。配置、数据规模和失败路径都要写出来，下一次遇到相似症状才能快速判断哪些条件仍然成立。
