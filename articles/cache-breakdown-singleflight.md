# 缓存击穿不是一句加锁就结束：我把保护放在哪一层

热点配置过期后几百个请求同时查 MySQL，给 Redis value 加锁又制造了新热点。进程内用 Promise 复用正在进行的查询，多实例再用短租约分布式锁，锁只保护谁回源，不串行整个业务。TTL 加 jitter 摊平过期时间，数据库失败时允许短暂返回 stale value。最后补命中率、回源并发、锁等待和 stale 次数四个指标，修复才有证据。
## 锁并不是越大越安全
第一次实现把业务函数整个包在分布式锁里，锁持有期间还包含序列化和网络请求，结果锁等待本身变成延迟尖峰。后面把锁缩到“声明回源者”这一步，其他请求等待同一个 Promise 或短暂读取 stale 数据。锁失效时还要保证旧持有者不会覆盖新值，因此写入带版本或 token。

TTL jitter 也不能写成完全随机，否则缓存寿命不可预测。我使用基础 TTL 加减一个小范围，并对热点 key 单独设置刷新窗口。刷新失败时延长 stale 的可用时间，但同时提高告警级别，让数据新鲜度和可用性有明确取舍。

检查清单：回源是否 singleflight；锁是否只包住必要区间；写入是否校验 token；TTL 是否有抖动；失败是否允许 stale；指标是否能看出回源风暴。



## 一致性取舍要写给业务看
缓存的 stale 数据不是技术团队偷偷决定的。配置、库存和权限的可接受过期时间不同，我把它们分成强一致、短 stale 和可异步刷新三类，并在接口文档写明行为。这样故障时不需要临时争论“旧数据能不能用”。

~~~bash
redis-cli TTL config:homepage
redis-cli INFO stats | grep keyspace
~~~

压测时要同时打过期 key 和热 key，观察回源峰值、锁等待和数据库连接。只测命中率会漏掉击穿发生的瞬间。


真正上线时还需要限制单个 key 的回源耗时和响应大小，防止缓存层修好后把慢查询结果再次放大。回源函数必须可取消，失败要带原因但不能把内部错误写进缓存。把这些边界提前写清，singleflight 才不会变成新的隐式队列。


我最后补了一个后台预热任务，但它不是每次失效都立即触发，而是只对高频 key 和即将过期的 key 工作。预热失败不会阻塞用户请求，仍由正常回源路径兜底。这样缓存层有主动刷新，也保留了简单可靠的被动读取路径。 


容量也需要随业务增长重新评估。热点 key 数量、单值大小和回源耗时一起增长时，单纯延长 TTL 会把压力推迟。每次容量调整都保留旧配置，必要时可以快速降级到 stale 或关闭预热。 


在实际维护中，我会把这类问题保留一份最小复现和一份线上证据。最小复现用来验证修复，线上证据用来确认修复没有改变其他路径。发布前再检查日志、指标、回滚和权限四件事，很多看似完成的改动，最后都卡在其中一件。


这份记录也提醒我，不要把解决方案写成只适用于当前机器的命令。配置、数据规模和失败路径都要写出来，下一次遇到相似症状才能快速判断哪些条件仍然成立。


在代码审查时，我会要求作者把这条经验落成一个可观察的检查点：一个测试、一个指标或一条部署校验都可以。只有能被下一次运行验证，经验才不会停留在事故后的口头总结。
