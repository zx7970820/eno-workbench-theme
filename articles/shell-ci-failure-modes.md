# Shell 脚本跑在 CI 里以后，错误处理才真正开始

本地能跑的脚本进 CI 后经常最后一步失败却显示成功。我开始使用 set -Eeuo pipefail、ERR trap 和 EXIT trap，临时文件通过 mktemp 创建并清理。set -e 在 if、while、命令替换中有例外，关键动作仍然显式检查返回值。网络抖动可以重试，权限错误不能重试。部署脚本拆成准备、校验、执行、回滚四段，每段都能 dry-run。代码：

~~~bash
set -Eeuo pipefail
trap 'echo failed at line $LINENO >&2' ERR
~~~
## set -e 没有替你做决定
管道中间命令失败、grep 找不到匹配、命令替换返回非零，都可能产生和直觉不同的行为。一个清理脚本里 grep 没找到旧文件，整个脚本提前退出，后续本该执行的部署锁没有释放。后来我把允许为空的命令写进 if，把必须成功的命令写成明确的检查。

CI 里还要处理信号。脚本启动的后台进程需要保存 PID，在 EXIT 和 TERM 中清理；日志不能只输出“failed”，要把目标、版本和最后一个动作写出来。重试函数要有最大次数和指数退避，不允许 while true 把 runner 占满。

发布前我会在一个空目录、一个已有旧版本的目录、网络断开的环境各跑一次；再检查临时文件、锁文件、权限和退出码。脚本越短越不代表越可靠，失败语义要写出来。



## 日志和返回码是接口
脚本输出给人看，也输出给 CI 解析。普通进度写 stdout，错误写 stderr，失败码保持稳定。路径一律用双引号，外部输入先校验，不把分支名直接拼进危险命令。

~~~bash
if ! command -v docker >/dev/null 2>&1; then
  echo 'docker is required' >&2
  exit 10
fi
~~~

我还会在临时目录里运行一次脚本，确认它不会依赖当前用户的 PATH、工作目录或历史环境变量。可复现比“我机器上能跑”更重要。


我还把 shellcheck 放进 CI，但没有把警告全部升级成阻塞，因为旧脚本里有些规则需要分批处理。新脚本必须通过静态检查，旧脚本按风险清理。自动化的目标是减少人工判断，不是制造另一套没人敢维护的红灯。


脚本的输入边界也要写清楚：版本号只允许字母、数字、点和短横线，路径不能来自未经校验的用户输入。CI token 不能通过 set -x 打出，必要时临时关闭 tracing。可靠脚本不只是返回正确，还要避免在失败时泄漏凭据或删除错误目录。 


脚本变更还要做反向测试：传入空参数、带空格路径、不存在文件、网络失败和中断信号。每个场景都检查退出码、日志和清理结果。这个成本很低，却能挡住很多只在生产出现的边界错误。 


在实际维护中，我会把这类问题保留一份最小复现和一份线上证据。最小复现用来验证修复，线上证据用来确认修复没有改变其他路径。发布前再检查日志、指标、回滚和权限四件事，很多看似完成的改动，最后都卡在其中一件。


这份记录也提醒我，不要把解决方案写成只适用于当前机器的命令。配置、数据规模和失败路径都要写出来，下一次遇到相似症状才能快速判断哪些条件仍然成立。
