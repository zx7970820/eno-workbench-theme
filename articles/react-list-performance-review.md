# React 列表卡顿的真正原因：不是把 key 换成 index

列表卡顿时大家先看 key，但这次 key 稳定，真正问题是每次筛选创建新对象和回调。Profiler 显示所有行重新渲染。React.memo 只有在 props 稳定时才有用。有效修改是稳定数据映射、把顶部状态移出行组件，数据量大时使用窗口化。key 负责协调正确，不能替性能优化背锅。
## key 警告只是入口
我曾经把 key 从 index 换成 id，滚动仍然卡。Profiler 的 flamegraph 显示父组件每次输入都创建完整 rows 数组，行组件拿到的新对象让 memo 失去意义。把筛选结果规范化成稳定引用，再把输入状态和列表状态拆开，才让重渲染数量下降。

窗口化也不是第一步就该上。它会改变测量、键盘导航和浏览器查找行为，先确认真实数据量和用户滚动方式。对固定高度列表可以简单，对动态高度列表需要额外测量和缓存，不能照抄一个库的 demo。

检查清单：先录 Profiler；确认 key 稳定；检查对象和回调引用；隔离输入状态；测量窗口化的可访问性；用真实设备比较滚动帧率。



## 不要只在开发机测
开发机上 500 行列表很顺，低端手机和真实网络下却不一样。我用真实数据量、慢 CPU 模拟和键盘导航复测，并观察输入是否掉帧。窗口化引入后，屏幕阅读器和查找功能也要重新确认。

~~~tsx
const visible = rows.slice(start, end)
return visible.map(item => <Row key={item.id} item={item} />)
~~~

性能修改最后要保留一个可回退开关，避免优化和业务改动同时上线后无法判断责任。


我还检查了交互语义：筛选后焦点是否保留，列表更新时屏幕阅读器是否得到合理提示，键盘上下移动是否仍然稳定。性能不能以牺牲可访问性换取。最后把 Profiler 截图和真实设备结果附在 PR，审查者能看到证据而不是只看优化代码。


这次评审还让我删掉了一处过度优化：一个只显示几十行的列表被强行窗口化，反而让滚动和测试复杂。性能预算应该来自真实设备、真实数据和可接受帧率，达不到预算再引入复杂方案。优化代码要有注释说明测量依据，避免未来的人把它当成无理由的技巧。 


我还为列表加了一个简单的性能回归数据集，包含长标题、缺图、重复更新和快速筛选。每次改组件先跑这个数据集，再在移动设备上手动滚动。这样不会因为一次理想数据的 benchmark 误判优化成功。 


在实际维护中，我会把这类问题保留一份最小复现和一份线上证据。最小复现用来验证修复，线上证据用来确认修复没有改变其他路径。发布前再检查日志、指标、回滚和权限四件事，很多看似完成的改动，最后都卡在其中一件。


这份记录也提醒我，不要把解决方案写成只适用于当前机器的命令。配置、数据规模和失败路径都要写出来，下一次遇到相似症状才能快速判断哪些条件仍然成立。


在代码审查时，我会要求作者把这条经验落成一个可观察的检查点：一个测试、一个指标或一条部署校验都可以。只有能被下一次运行验证，经验才不会停留在事故后的口头总结。


如果这条检查没有自动化入口，就先补一个最小脚本或测试。它不需要覆盖所有情况，但必须能在改动后重复运行，并把失败原因留在构建日志里。
