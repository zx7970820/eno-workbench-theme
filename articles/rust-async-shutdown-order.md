# 把 Rust async 任务关干净：取消、JoinHandle 与退出顺序

Tokio 服务收到信号后先停止接收新请求，再通知后台任务，最后等待它们退出。JoinHandle 要被保存，任务要在 IO、队列等待和批处理循环检查取消信号，每个任务设置最大等待时间并打印名字。取消不是异常，而是正常控制流。只等待 CancellationToken 不等于服务已经关干净。
## 退出测试比代码更容易暴露问题
我用 docker stop 模拟 SIGTERM，发现服务在 10 秒后仍被强制杀掉。原因是一个任务卡在没有取消语义的 channel recv 上，主任务以为它会结束，实际上 JoinHandle 一直 pending。修复后把 select! 加到每个长期等待点，并为每个阶段输出 shutdown span。

数据库连接、HTTP listener 和指标 exporter 的关闭顺序也不同。先拒绝新请求，再等待正在处理的请求，最后关闭连接和 exporter，日志才有机会刷完。超过总预算时必须接受部分任务被放弃，并明确这是可观察的超时而不是静默失败。

检查清单：每个后台任务是否可取消；JoinHandle 是否被等待；listener 是否先停止接收；连接是否在预算内关闭；SIGTERM 和 Ctrl-C 是否走同一流程；强制退出前是否打印未完成任务。



## 让取消有测试证据
我给每个任务写一个测试：发出取消后，任务必须在预算内返回；如果下游永远 pending，测试应该失败而不是一直挂住。测试使用 tokio::time::timeout 包住 JoinHandle，避免 CI 被一个遗漏的 await 拖死。

~~~rust
assert!(timeout(Duration::from_secs(2), handle).await.is_ok());
~~~

日志中记录开始关闭、任务完成和强制放弃三种事件，线上才能知道是正常退出还是达到预算。


任务退出还要考虑 panic。JoinHandle 的结果不能被静默丢弃，任务异常应当进入统一错误报告；但一个非关键 exporter 失败不应该阻止核心服务停止。退出策略要区分关键任务和可放弃任务，而不是所有 handle 同等对待。


我也避免在 Drop 里做异步清理，因为 Drop 没有可靠的 await 语义。需要等待的资源由显式 shutdown 方法负责，Drop 只做同步兜底。调用方必须处理 shutdown 返回值，不能把关闭失败吞掉。这样退出流程既可测试，也不会靠运行时偶然调度。 


我还把退出预算设成配置而不是常量，批处理服务可以更长，HTTP 边缘服务更短。配置启动时打印但不打印凭据，部署时可以根据流量类型选择。这样同一套 shutdown 逻辑适配不同服务，不必复制粘贴。 


在实际维护中，我会把这类问题保留一份最小复现和一份线上证据。最小复现用来验证修复，线上证据用来确认修复没有改变其他路径。发布前再检查日志、指标、回滚和权限四件事，很多看似完成的改动，最后都卡在其中一件。


这份记录也提醒我，不要把解决方案写成只适用于当前机器的命令。配置、数据规模和失败路径都要写出来，下一次遇到相似症状才能快速判断哪些条件仍然成立。
