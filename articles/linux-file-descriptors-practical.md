# Linux 上的文件描述符：服务为什么突然打不开新连接

EMFILE 不代表机器没内存，而是进程的文件描述符配额耗尽。先看 /proc/PID/limits，再统计 /proc/PID/fd，最后用 lsof 看增长的是 socket、文件、pipe 还是 eventfd。提高 LimitNOFILE 只能延后故障，真正修复是关闭异常路径、限制连接池，并对 fd 数量报警。文件描述符和内存、线程一样，需要配额、观测和回收。命令：

~~~bash
cat /proc/$PID/limits | grep 'open files'
ls /proc/$PID/fd | wc -l
~~~
## 我差点只改了 ulimit
查到进程上限后，我准备直接把 systemd 的 LimitNOFILE 调大，但 lsof 显示增长最快的是匿名 pipe，根因是一个子进程没有 wait。提高上限只会让更多子进程堆积。修复后还要确认服务重启时 systemd 配置真的生效，并比较启动前后的 limits。

连接泄漏通常和超时、异常路径、HTTP keep-alive 配置一起出现。测试里我让下游故意不返回，再观察 fd 数量是否回落。对于长期运行的服务，fd 曲线应该和活跃连接有关系，而不是只在故障时临时执行命令。

检查清单：看进程和系统两个上限；按类型统计 fd；检查子进程回收；验证连接池和超时；让监控记录 fd 使用率；在重启和滚动发布中复核限制继承。



## 监控要提前到趋势阶段
故障时执行 lsof 已经晚了。我给服务增加 fd 使用率、活跃连接、连接池空闲数和子进程数四个指标，按进程维度画趋势。fd 使用率超过 70% 持续十分钟就提醒，超过 90% 才升级为故障。

~~~bash
for fd in /proc/$PID/fd/*; do readlink "$fd"; done | sort | uniq -c | sort -nr | head
~~~

滚动发布还要确认新进程继承了正确限制，旧进程退出后 fd 是否真正释放。否则看似换了实例，泄漏只是换了一个 PID。


定位完成后，我没有只改应用代码，也把 systemd 配置和运维检查加入部署仓库。服务启动时打印当前 soft/hard limit，方便从日志确认实际配置。故障排查最好能在一条命令里看到限制、使用量和增长类型。


服务稳定后我做了一次故障演练：人为降低进程 fd 上限，再建立大量连接，确认告警能在服务完全失效前触发。演练同时验证日志是否能区分 accept 失败、连接池耗尽和子进程泄漏。能复现的问题才有资格进入自动化检查。 


如果 fd 类型是 socket，还要对比连接状态。大量 CLOSE_WAIT 通常指向应用没有 close，TIME_WAIT 过多则可能是短连接策略问题。把 fd 总量和 ss 的状态分开看，定位会比单独看一个数字快很多。 


在实际维护中，我会把这类问题保留一份最小复现和一份线上证据。最小复现用来验证修复，线上证据用来确认修复没有改变其他路径。发布前再检查日志、指标、回滚和权限四件事，很多看似完成的改动，最后都卡在其中一件。


这份记录也提醒我，不要把解决方案写成只适用于当前机器的命令。配置、数据规模和失败路径都要写出来，下一次遇到相似症状才能快速判断哪些条件仍然成立。
