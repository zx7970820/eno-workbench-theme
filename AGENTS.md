## Durable design direction

- Selected visual target: Product Design ideation option 1, the dark editorial console in `C:\Users\Administrator\Documents\Codex\2026-08-24\w-x20\work\selected-design-option-1.png`.
- Product positioning: a frontend-led personal technology blog, with backend, Shell, Rust, Linux, infrastructure, and engineering-practice topics as supporting areas rather than the primary identity.
- Content taxonomy should comfortably include frontend, backend, Shell, Rust, Linux, infrastructure, and engineering practice.
- Preserve the dense dark workbench layout, restrained mint/violet accents, sharp borders, and code-oriented typography while avoiding obvious frontend-only branding.
- Every visible navigation item, article link, search control, category, and call to action must resolve to real WordPress content or a real WordPress route. Remove any control that cannot be implemented truthfully; do not use fictional series, progress, counts, social profiles, or articles as decoration.
- Support light and dark modes. Use the native View Transition API for a smooth theme reveal when available, respect `prefers-reduced-motion`, provide a no-animation fallback, follow the system preference on first visit, and persist an explicit visitor choice locally.
- User preference (2026-08-25): the dark theme is branded “eno 的小黑屋”; the light theme is branded “eno 的小白屋”. Keep the name change visible wherever the site brand is shown.
- Prefer interactive additions that help reading or debugging (for example, a real table of contents, code copying with a fallback, sharing, or explanatory diagrams) over decorative animation.
- Keep the project as a complete local repository: WordPress theme, content/import plugin, reproducible Docker-based WordPress + database environment, deployment notes, and content sources belong together.
- Editorial voice should be conversational and experience-led, avoiding formulaic AI-style sectioning and filler. The long-term topic mix can include frontend, backend, Shell/Linux, Rust, systems, and engineering practice, but the current published set is intentionally narrowed to frontend and tooling; backend, Shell/Linux, observability, and data-cache seed posts are retired as drafts for now and can be reintroduced later. Seeded publication dates should span 2019 through the present instead of clustering on one import date.
- Current editorial emphasis: grow the frontend section around React and Vue rather than spreading the initial set evenly. React coverage should include pre-16.8 class lifecycles and `shouldComponentUpdate`, then Hooks from basic state and closures through effect cleanup, memoization, and Fiber scheduling. Vue coverage should include Vue 2 Observer/Dep/Watcher internals, computed/watch and `dirty`, watcher roles, and virtual-DOM patching. Rust seed posts are retired from the current published set, but the taxonomy remains available for future writing.
- Existing seeded articles should be treated as a starting point, not finished editorial work: most need substantial rewriting for real technical depth, concrete trade-offs, runnable examples, debugging evidence, and experience-led conclusions. Avoid short filler posts.
- Finish and review one article at a time: after each article is written or materially rewritten, verify framework-specific APIs and code against the underlying semantics, scan for cross-framework terms and placeholders, sync Markdown to HTML, reimport the local WordPress post, and inspect its rendered route before starting the next article.
- Historical framing is part of accuracy: write from the version context available at the article's date instead of using hindsight. A pre-React-16.8 note should not talk as if Hooks already existed; a Vue 3 note dated before the 2020-09-18 stable release must call out the Vue Next/beta status.
- Historical notes should open with the concrete debugging question or observation, not a defensive date/version disclaimer; keep the beta/stable timeline in one natural sentence and then follow the source path.
- Article rewrites should sound like a real engineer thinking aloud: lead with a specific incident or question, include uncertainty and failed attempts where useful, and avoid repetitive AI-shaped checklists, generic conclusions, and inflated sectioning.
- Editorial feedback to preserve: write as a personal technical notebook rather than a formal report. Do not add unnecessary commit hashes, branch metadata, bibliography/reference sections, or citation link lists; explain what was actually tried and learned in a natural voice. Article pages should not expose a comment module.
- Avoid AI-shaped endings: do not finish with “I would adopt these three principles,” generic takeaways, or a prescribed framework for the reader. End with a specific personal reaction, a concrete next step, or an honest unresolved edge.
- Audit and improve interaction quality across desktop and mobile: navigation, search, category links, article reading, theme switching, focus states, and touch targets should feel intentional and remain truthful to real WordPress routes.
- User preference (2026-08-25): do not expose year-archive navigation or archive panels in the visible blog UI; keep articles discoverable through the home feed, categories, and search.
- User preference (2026-08-25): never silently truncate a long article list; the home feed and any multi-page category/search result must expose real, working pagination without duplicate featured articles.
- User preference (2026-08-26): animate article list, featured, and adjacent-article navigation into the article title with a shared-element View Transition when supported; retain safe fallback and respect reduced motion.
- User feedback (2026-08-26): the shared-title transition is acceptable in Chrome, but its final frames must not retain a translucent old-title snapshot; finish the opacity handoff before the positional animation ends to avoid ghosting or a last-frame jump.
- Implementation decision (2026-08-27): Chrome 151 aborted even a minimal cross-document View Transition with `InvalidStateError`, while same-document transitions remained healthy. Article-title navigation therefore progressively enhances real WordPress routes by fetching and swapping the route-content region inside `document.startViewTransition()`, updating browser history, and falling back to native navigation on unsupported/reduced-motion/error paths. Do not re-enable `@view-transition { navigation: auto }` without first proving the minimal cross-document case works in the acceptance browser.
- User feedback (2026-08-26): desktop Chrome must pair the card title with the detail heading before the new page is captured. Do not actively call `skipTransition()` for missing activation metadata or an absent optional match, and do not rely solely on a late `pagereveal` mutation for the destination heading.
- User preference (2026-08-27): the browser document title must switch with the theme brand (`eno 的小黑屋` / `eno 的小白屋`) while retaining the current route title; the visible page uses the generated Z favicon and a hidden/page-leaving state uses the generated X favicon.
- User feedback (2026-08-29): navigating from a scrolled home/search list into an article must not expose a smooth window scroll before the shared-title transition; keep normal page scrolling smooth, but position route snapshots instantly inside the transition.
- User feedback (2026-08-27): browser Back/Forward between an article and its originating card list must use the reverse shared-title transition instead of a hard reload, restoring the list scroll position so the large article title visibly shrinks back into the original card title.
- User feedback (2026-08-27): the shared title must show a continuous, perceptible font-size/scale change in both directions. Bring the incoming title snapshot into the handoff early enough that the last frame does not abruptly switch text sizes, while still removing the outgoing snapshot before the animation ends.
- Deployment requirement (2026-08-27): the public WordPress site must support HTTPS and redirect HTTP traffic to HTTPS after the certificate and WordPress canonical URLs are updated and verified.
- The local WordPress + MariaDB environment is the authoritative development and acceptance target. The Vite/Sites prototype under `src/` is only a visual prototype and must not be presented as the blog's local mirror or deployed as the WordPress site.
- Follow the release sequence: start the local WordPress stack, verify real routes and admin/content behavior there, back up the live site, then deploy the same theme/importer artifacts and re-verify online.
